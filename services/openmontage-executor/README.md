# ORKY OpenMontage Executor

This service is the server-side bridge between ORKY Studio and an actual OpenMontage workspace.

It is intentionally separate from the Next.js runtime. OpenMontage is an agent-driven production repository: the agent reads `AGENT_GUIDE.md`, selects a pipeline, operates tools, writes checkpoints and stops at human approval gates. The executor provides persistence and an HTTP control plane around that process; it does **not** reimplement OpenMontage's creative orchestration in Python.

## Contract

Authenticated endpoints:

```text
POST /jobs
GET  /jobs/:jobId
POST /jobs/:jobId/approval
GET  /jobs/:jobId/render
```

Public health endpoint:

```text
GET /health
```

`POST /jobs` accepts the `orky.openmontage.production-plan.v1` manifest generated by ORKY. The service creates a durable job and launches the configured coding agent in `/opt/openmontage`.

At each OpenMontage approval gate, the agent writes a small bridge signal and exits. ORKY displays the gate. When the user approves or asks for revision, `/approval` launches a fresh headless agent turn that resumes from OpenMontage checkpoints.

This one-turn-per-gate model is deliberate: OpenMontage's own project/checkpoint files are the durable production state rather than a fragile long-lived terminal session.

## Default image

The Dockerfile pins upstream OpenMontage to:

```text
calesthio/OpenMontage
1bab711820828c2e5fc1f87ed274a32587cb048f
```

The image also installs the official Codex CLI as the default headless agent driver. You can replace the driver without changing ORKY by setting `OPENMONTAGE_AGENT_COMMAND_JSON`.

## Required environment

```env
OPENMONTAGE_EXECUTOR_TOKEN=<long random secret>
OPENMONTAGE_ROOT=/opt/openmontage
OPENMONTAGE_EXECUTOR_DATA=/data/openmontage-executor
OPENMONTAGE_EXECUTOR_PUBLIC_BASE_URL=http://openmontage-executor:8787
OPENMONTAGE_EXECUTOR_MAX_CONCURRENT=1
OPENMONTAGE_AGENT_TIMEOUT_SECONDS=7200
```

For the default Codex driver, configure the authentication expected by Codex in the container. An API-key based deployment normally injects the provider credential as a secret. A ChatGPT-authenticated CLI deployment can instead persist its CLI home in a private volume.

OpenMontage provider secrets (`FAL_KEY`, `ATLASCLOUD_API_KEY`, `KLING_API_KEY`, TTS keys, etc.) are also injected only into this executor container. Do not expose them as `NEXT_PUBLIC_*` variables.

## Alternate agent driver

`OPENMONTAGE_AGENT_COMMAND_JSON` is a JSON array executed directly with `subprocess.Popen(shell=False)`.

Supported placeholders:

```text
{prompt}
{prompt_file}
{project_root}
{project_id}
{job_id}
```

Example shape for another CLI:

```env
OPENMONTAGE_AGENT_COMMAND_JSON=["my-agent","run","--cwd","{project_root}","--prompt-file","{prompt_file}"]
```

The executable must be present in the image/container. The default driver is equivalent to a non-interactive Codex execution inside this dedicated production container.

## Approval protocol

The agent is explicitly instructed to stop and write a bridge signal when OpenMontage requires a human decision. Example:

```json
{
  "status": "awaiting_approval",
  "stage": "proposal",
  "progress": 20,
  "estimatedCostEur": 1.2,
  "actualCostEur": 0,
  "awaitingApproval": {
    "gate": "proposal",
    "summary": "Options, costs, tradeoffs and recommendation."
  }
}
```

A completed job must point to a real render inside `OPENMONTAGE_ROOT`:

```json
{
  "status": "completed",
  "stage": "final-qc",
  "progress": 100,
  "actualCostEur": 1.2,
  "renderPath": "projects/my-production/renders/final.mp4"
}
```

The executor refuses completion when the file does not exist or escapes the OpenMontage checkout. It computes SHA-256 and uses `ffprobe` for duration/dimensions when available.

## Persistence and restart recovery

Durable state lives under `OPENMONTAGE_EXECUTOR_DATA`:

```text
jobs/       job state
manifests/  canonical ORKY manifests
prompts/    exact agent prompts
signals/    agent → executor gate/final signals
logs/       process output
```

If the executor restarts while a job is `queued` or `running`, it re-queues the job. The new agent turn is told to resume from OpenMontage's checkpoints rather than regenerate completed stages.

## Render delivery

`GET /jobs/:jobId/render` requires the executor bearer token and supports HTTP Range requests. ORKY should proxy this endpoint through the signed user-bound job handle; the browser should not receive the executor token or internal service URL.

## Security boundaries

- Executor API requires a bearer token.
- It runs the agent with `shell=False`; the executable/arguments are administrator configuration, never user input.
- The browser never receives the raw OpenMontage job id from ORKY.
- The agent receives a constrained, versioned manifest rather than arbitrary shell commands from the user.
- Render paths are constrained to `OPENMONTAGE_ROOT`.
- The service should run on a private Docker/Coolify network. Expose only ORKY's public render proxy.
- The default Codex command has broad permissions **inside this dedicated container** because OpenMontage needs to execute its own tools. Do not mount the Docker socket, host filesystem, SSH keys or unrelated application secrets into this container.
